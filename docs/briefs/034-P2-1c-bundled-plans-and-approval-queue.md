# /tdd brief — bundled_action_plans_and_approval_queue

## Feature
Build the **O-3 bundled-plan layer** on top of the 2.1b single-action chokepoint, plus the **Human
Input Queue read model**: `submit_action_plan(ActionPlan) → PlanAck` over the GatewayPort; a thin
durable `action_plans` metadata table + a nullable `plan_id` FK on `action_requests` (single action
= `plan_id` NULL); **step-by-step + approve-all approval** (approve-all excludes critical/risk-4);
the **`proj_approval_queue` projector body** (re-homed from 1.2 — folds the Gateway's approval
events into the Human Input Queue read model, `sort_key` risk-DESC then age); and the
**approval-queue subscribe-delta** (the gateway-event → `ProjectionDelta` broadcast path deferred
from 2.1b). The plan = grouping-over-`action_requests` (lead-agreed Q1); each step is a full
`ActionRequest` emitting its own `Action*` events; the plan is a durable grouping, **not** a new
event type.

> **Scope note:** 2.1c is the LAST sub-slice of the split task 2.1 (2.1a freeze ✅ `a45f2e3`; 2.1b
> single-action chokepoint ✅ `0578d60`). It consumes the frozen §6.2 `ActionPlan`/`ActionPlanStep`/
> `ActionDependency`/`ApprovalMode`/`ApprovalScope` (all landed 2.1a) + the frozen `Approval` model
> (which already carries `plan_id: Option` + `scope` — the plan dimension was frozen 2.1a; 2.1b's
> single-action TABLE under-realized it). **security-reviewer on EVERY layer** (INV-SEC-1 — approval
> is the safety gate; an approve-all cascading execution to N steps is safety-sensitive).

## Acceptance criteria (what "done" means)
**L1 — the `proj_approval_queue` projector + registration + the approval-queue subscribe-delta** (read-model; no contract change; lights up the EXISTING 2.1b single-action approvals + closes the 2.1b→2.1c read-model deferrals):
- [ ] An `ApprovalQueueProjector` (`name() == "approval_queue"`, table `proj_approval_queue`) is registered in `projections::projectors()` and folds the Gateway approval events: `ActionApprovalRequested` → UPSERT a queue row at `awaiting_approval`; `ActionApproved`/`ActionDenied`/`ActionExpired` → advance the row's `status` (the resolved/terminal approval **leaves the open queue** — see Q4 for remove-vs-mark). **The row's MUTABLE `status` is derived from the EVENT TYPE; only IMMUTABLE fields (`risk_level`, `requester_type`/`requester_id`, `project_id`, `expires_at`) are read from the sibling `action_requests`/`approvals` rows in the same txn** (rebuild-safe — those fields never change post-submit; the graph-reads-`object_refs` precedent). Idempotent upsert (rebuild-equivalent).
- [ ] `sort_key` orders **risk DESC, then age (oldest-first)** — the Human Input Queue ranking (AG sec 8 / §14.3); the projector populates it (see Q5).
- [ ] The **subscribe-delta** fires: a committed gateway approval transition publishes a `ProjectionDelta{projection: ApprovalQueue, kind, id/row}` on the broadcast SOURCE (1.6b) **after commit** (publish-after-commit, never back-pressuring the writer — forbidden #3); the socket SERVE push (1.6d) then streams it. This closes 2.1b Step-9 flag (b).
- [ ] Rebuild-equivalence: `rebuild()` reproduces identical `proj_approval_queue` state (deterministic fold).

**L2 — `submit_action_plan` + the plan schema (MIGRATION_8) + `PlanAck` + CONTRACT 0.16.0→0.17.0** (the O-3 mutation path):
- [ ] `MIGRATION_8`: the thin `action_plans` table (`plan_id` `aplan_` PK, `title`, `overall_risk`, `approval_mode`, `created_at`); `action_requests.plan_id` nullable FK (→ `action_plans`; single action = NULL); **generalize `approvals` + `proj_approval_queue` to `action_request_id` NULLABLE + add `plan_id`** (so a plan-level approve-all approval — `scope=Plan`, `plan_id` set, `action_request_id` NULL, per the FROZEN §6.2 `Approval`) can persist; `SUPPORTED_USER_VERSION` 7→8. (See Q2 for the SQLite nullable-change shape + whether to split into two migrations.)
- [ ] `submit_action_plan(ActionPlan) → PlanAck` runs as **ONE atomic gateway txn** (fail-closed — the whole plan persists or nothing): insert the `action_plans` row; for each step insert its `action_requests` row (`plan_id` set; `inputs`/`resource_refs` §15-row-redacted via `gtx.redact_row`, rule #3/#4) + emit `ActionRequested`; advance Submitted→PolicyDecided→AwaitingApproval (R-9 guarded, reusing 2.1b `request::update_status`); open the approval object(s) per `approval_mode` (Q3) + emit `ActionApprovalRequested`. Any step failure rolls the whole txn back (no partial plan).
- [ ] `PlanAck` is a NEW `shared/src/ipc.rs` wire type (Q1 shape) — the §6.1 `submit_action_plan` result; **CONTRACT_VERSION 0.16.0 → 0.17.0** (additive) + schema regen + 3-way verify green.
- [ ] **§2.5-seam schema-snapshot** for `PlanAck` (field-name set == checked-in snapshot, `spec(§6.1)`-tagged) — `PlanAck` is on the §2.5-seam GatewayPort wire surface. No re-snapshot of `ActionPlan` (frozen 2.1a, untouched).
- [ ] `submit_action_plan` reachable from the real IPC dispatch (`ipc/methods.rs`) via a new `GatewayPlanSubmit` write-actor command (Step 7.5).

**L3 — step-by-step + approve-all approval mechanics** (the O-3 approval semantics):
- [ ] `approve(approval_id, step_id?)`: approving a **step approval** drives that one step Approved→Queued→execute (stub) → `ActionApproved`/`ActionStarted`/`ActionSucceeded` (reusing 2.1b `approve`/`execute`); approving a **plan-level approve-all approval** cascades to **every non-critical step** of the plan (each step Approved→Queued→executed via the stub, each emitting its own `ActionApproved` tied to that step's `action_request_id` + the shared plan-approval `approval_id`).
- [ ] **Critical (risk-4) steps are NEVER in approve-all** (§6.2/sec 11.5): a risk-4 step gets its OWN per-step approval at submit time and is NOT covered by the plan-level approve-all approval; approving approve-all leaves critical steps `awaiting_approval`.
- [ ] `deny(plan_approval_id, reason)` on a plan-level approval denies the covered steps (terminal; executor never invoked); an expired plan approval → `ActionExpired` per covered step, none executed (§17; fake clock).
- [ ] All mutation methods reachable from `ipc/methods.rs`; `/preflight` clean; **security-reviewer EVERY layer** (INV-SEC-1).

## Things to flag at Step 2.5
1. **Q1 — `PlanAck` shape.** §6.1 says `PlanAck{plan_id,...}`. My default vote: `PlanAck{ plan_id: String, steps: Vec<PlanStepAck> }` where `PlanStepAck{ step_id: String, action_request_id: String, status: ActionRequestStatus }` — mirrors `ActionAck{action_request_id,status}`, gives the client the minted per-step ids (to `preview_action`/track each) + the plan handle. `#[serde(deny_unknown_fields)]`, optionals as `null`. Flag if you'd add `approval_ids`/`overall_status` now (I'd defer — additive-later).
2. **Q2 — MIGRATION_8 shape (the nullable change).** SQLite can't drop `NOT NULL` via `ALTER`; making `approvals.action_request_id` nullable + adding `plan_id` needs a **table-rebuild** (CREATE new → `INSERT … SELECT` → DROP → RENAME → recreate `ix_approvals_action`). `proj_approval_queue` is a *projection* (rebuildable) → simplest is DROP+CREATE with the new shape (the L1 projector is NEW so its offset starts at 0 and catch-up re-folds the whole log — no stale-offset). My default vote: **one `MIGRATION_8`** carrying action_plans + `action_requests.plan_id` + the approvals rebuild + the proj_approval_queue reshape (so the L1 projector writes the final shape from the start). Flag if you prefer schema-with-consumer (proj reshape in L1's migration, action-side in a 2nd migration) — both are forward-only + additive.
3. **Q3 — which approval objects `submit_action_plan` opens, per `approval_mode`.** My default vote (faithful to frozen §6.2 `Approval` + §6.1 `approve(approval_id, step_id?)` + sec 11.5): **`StepByStep`** → one per-step approval each (`action_request_id` = step, `plan_id` set, `scope=Plan`). **`ApproveAll`** → ONE plan-level approval (`action_request_id` NULL, `plan_id` set, `scope=Plan`) covering the **non-critical** steps + a SEPARATE per-step approval for **each critical (risk-4)** step. `Mixed`/`Blocked` → flag (my lean: 2.1c treats `Mixed` as `StepByStep` and `Blocked` as "open no approvals, plan stuck `awaiting_approval`" — or defer both to a later slice with a clear marker). This is the load-bearing modeling call — review carefully; it's conformance to the frozen model (action_request_id already `Option`), not a new contract.
4. **Q4 — resolved approvals: remove-from-queue vs status-marked.** The Human Input Queue shows OPEN items. My default vote: the projector keeps the row but advances `status` (approved/denied/expired) and the **OPEN-queue query filters `status='awaiting_approval'`** (the row stays for audit/history; `proj_audit_trail` is the timeline, but keeping the queue row status-marked is cheap + lets the ui show "just resolved"). Flag if you'd rather DELETE the row on resolve (leaner queue table; loses the just-resolved view).
5. **Q5 — `sort_key` computation.** My default vote: a lexically-sortable string `format!("{}_{}", 4 - risk, requested_at)` so a single `ORDER BY sort_key` gives risk-DESC-then-age-ASC (matches `ix_approval_queue_open(status, risk_level, requested_at)`; the index can serve the query directly too). Flag if you'd leave `sort_key` NULL and rely solely on the index-ordered query.
6. **Q6 — the approval-queue subscribe-delta seam.** The gateway command arms (`GatewaySubmit`/`Approve`/`Deny`/`PlanSubmit`) bypass `Command::Append`, so they never hit `deltas_for_append` today. My default vote: the gateway pipeline **accumulates the `ProjectionDelta`s it produced** (one `ApprovalQueue` Upsert per approval row it touched, keyed by `approval_id` — derivable from the `gtx.append`ed intents' `approval_id` + event_type) and **returns them alongside its ack**; the `run_actor` gateway arms publish them **post-commit** (mirroring the `Command::Append` publish-after-commit + the `deltas_for_append` derivation pattern). Flag the alternative (route gateway appends through a shared delta-deriving append wrapper). Keep it a "something changed" nudge — the id only; the subscriber re-reads via `get_projection` (consistent with the lag-resync policy).
7. **Q7 — no plan-level event type.** AG §17.1 lists no `ActionPlanProposed`/`PlanApproved`; the §17.2 `actionPlanId?` is optional and there is **no `action_plan_id` envelope column** (the frozen envelope is not touched). My default vote: **emit NO new event type in 2.1c** — each step emits its own `Action*` events (tied to its `action_request_id`); the plan grouping lives in `action_plans` + `action_requests.plan_id` (reconstructable by join). This keeps the CONTRACT bump `PlanAck`-only. Flag if you want an `ActionPlanProposed{plan_id,title,step_count,approval_mode}` audit anchor now (it would carry `plan_id` in the payload, not the envelope — a 2nd new event type + a heavier contract bump).
8. **Q8 — projector reads sibling registry rows.** The `ApprovalQueueProjector` reads IMMUTABLE fields (`risk_level`, `requester_*`, `project_id`, `expires_at`) from `action_requests`/`approvals` (same txn) while deriving MUTABLE `status` from the event type. My default vote: **sibling-read the immutable fields** (rebuild-safe — they never change; the graph-reads-`object_refs` precedent; reads via raw SQL, not importing gateway code). Flag the alternative (extend the `ActionApprovalRequested` payload to carry them — rejected: duplicates registry data, bloats the event, needs a payload contract change).
