# /tdd brief — terminal_channel_pty_host_backpressure

## Feature
Stand up the daemon-side **§6.4 Terminal Channel** spine: freeze the multiplexed terminal wire frames (`ServerFrame::TerminalOutput` + input/control + the `TerminalProcessExited` observation event) as the next §2.5-seam contract bump, build the daemon **PTY session host** (`portable-pty` behind a `FakePty` seam, display-only per safety #9), and wire **app-level backpressure** (watermark pause/resume + ~30 fps batching) so a high-output child bounds the buffer instead of OOM/stalling. This is the ungated ui-track unblocker — ui 6.3d's xterm.js host consumes the frozen Terminal Channel at its resume.

**L2 — the daemon PTY session host (one commit; no contract change):**
- [ ] `daemon/src/terminal/mod.rs` (NEW) defines a **`Pty` trait** (object-safe, `Box<dyn>` — the `ActionExecutor`/`HarnessAdapter` seam precedent): `{spawn(cmd, cwd, size), write(bytes), resize(size), read()->bytes-or-EOF, kill}` (async where the lifecycle implies). A **`PortablePtyHost`** impl wraps `portable-pty` (add the dep to `daemon/Cargo.toml`) and a **`FakePty`** test double drives spawn/output/exit deterministically (§14 seam — scripted output chunks + a scripted exit, no real child).
- [ ] On detected child exit (portable-pty waitpid / reader EOF), the host **emits `TerminalProcessExited`** via the write-actor append (the §15-gated observation path) — `exit_code`/`signal` from the OS, **never** inferred from output bytes (safety #9).
- [ ] `terminal_id` is **minted as a daemon-internal runtime handle** (NOT one of the frozen 22 IDs — it's connection/session-scoped + re-minted on resume, the `subscription_id` precedent; Step-2.5 Q1). Use the injectable `IdGen`/a typed newtype; do **not** add a kind to `IdKind` (that would be a LOCKED-22 escalation).
- [ ] `daemon/src/lib.rs` registers `pub mod terminal;`. The module is **display-only** — it exposes no status/lifecycle-derivation API (a test asserts the public surface is byte-IO + exit-signal only; forbidden #4).
- [ ] Unit tests drive `FakePty`: spawn→read streams the scripted chunks; `write` reaches the child; scripted exit → exactly one `TerminalProcessExited` with the right `exit_code`; reader EOF is a clean terminal state (no panic/hang).

**L3 — app-level backpressure flow control (one commit; no contract change):**
- [ ] A **bounded output buffer** per terminal with high/low **watermarks**: crossing high → emit a `TerminalControlFrame{pause}` (and stop draining the PTY reader into the channel); draining below low → `{resume}`. The PTY reader **never** unbounded-buffers — at the high watermark it stops reading the child (OS pipe backpressure propagates to the agent), it does **not** grow an in-memory queue → **no OOM, no stall** (the 3.4 edge acceptance).
- [ ] Output is **batched at ~30 fps** (coalesce reader chunks into one `TerminalOutputFrame` per ~33 ms tick) rather than one frame per read — the `seq` increments per emitted frame.
- [ ] The pause/resume + batch decision is a **pure classifier** (`next_terminal_action(buffer_len, high, low, paused) -> Emit | Pause | Resume | Hold`) — unit-tested at the watermark boundaries with NO real timing (LESSON §12; mirror `next_push_action`). The reader→channel pump applies the classifier; the classifier itself is timing-free.
- [ ] The terminal reader/pump **never back-pressures the write-actor** (forbidden #3 / LESSON §9) — Terminal Channel flow control is entirely between the PTY child and the socket, independent of the DB write path.
- [ ] All unit tests (L1 `shared/tests/` + L2/L3 `daemon/src/terminal/` + a `daemon/tests/terminal.rs` integration) pass; `/preflight` clean (fmt + clippy `-D warnings` + full suite + `emit_schema` no-diff).
- [ ] Cross-doc invariant rows written by the orchestrator at Step 9 (see below).

## Things to flag at Step 2.5
1. **`terminal_id` representation (contract-surface — do not take silently).** A runtime handle minted by the daemon (NOT one of the frozen 22 IDs) vs a new `IdKind`. **My default vote: a daemon-minted runtime handle** (a typed newtype over a ULID/u64 via `IdGen`), the `subscription_id` precedent — a terminal is connection/session-scoped + re-minted on resume, not a persisted domain entity, so it does **not** belong in the LOCKED-22. Adding an `IdKind` would be a LOCKED-22 contract escalation (the `workflow_run_id` precedent) — avoid unless you/`security-reviewer` see a durable-cross-restart need; if you do, **stop and escalate** (category #4) rather than minting a 23rd ID.
2. **Terminal-byte wire encoding (load-bearing; flagged to the lead as an away-authority decision).** JSON-base64 (rides the existing `ServerFrame` codec) vs a binary fast-path. **My default vote: JSON-base64 MVP now**, binary fast-path **additively deferred to 3.5** (the throughput benchmark) — this is exactly what the `ServerFrame` doc comment + LESSON §7 ("Terminal encoding = Phase-3 measured") already anticipate: reuse the proven 4-byte-len+JSON mux, prove the end-to-end path, let the 3.5 numbers justify binary (additive variant + CONTRACT bump) only if JSON-base64 can't hit the xterm.js 5-35 MB/s ceiling. Reversible + additive, not a one-way door.
3. **`TerminalProcessExited` scope.** Emit the observation event only vs build the §17 cascade (SessionFailed → ActionFailed → lease release). **My default vote: event only** — 3.4 owns the Terminal Channel + the PTY-death *signal*; the §17 failure-mode state machine is **Phase 4** (it consumes this event). Don't reach into Phase-4 survival here.
4. **`Pty`/`FakePty` seam shape.** Object-safe `Box<dyn Pty>` (the `ActionExecutor`/`HarnessAdapter` precedent) vs an enum vs generics. **My default vote: `Box<dyn Pty>`** — matches the established daemon seam style + lets `FakePty` swap in for §14 determinism. Keep it **sync or async** consistent with how the pump task drives it (the reader loop is a Tokio task — async read is natural; confirm against `portable-pty`'s blocking reader → likely `spawn_blocking` the reader, the write-actor-thread precedent LESSON §9).
5. **Watermark thresholds + tick rate.** **My default vote: high/low watermark as a small bounded byte budget (e.g. 256 KiB / 64 KiB) + a ~33 ms (30 fps) batch tick**, both **named consts** (not magic numbers) so 3.5 can tune them with throughput data. The exact numbers aren't load-bearing now (no budget until 3.5 — §18 deferred-budget note); pick sane consts + a comment pointing at 3.5.
6. **`attach_terminal` executor binding (Step 7.5 reach).** Does the live `session.attach_terminal` → `PortablePtyHost` binding fit this slice, or is it genuinely the next integration step? **My default vote: build the host + channel mechanism here, reachable via `FakePty` + the pump test; bind the catalog executor when the per-session drive loop lands (3.2/3.3 / a terminal-executor slice)** — state it honestly at Step 7.5 (the registered-but-driven-next precedent, like 3.1's projector). If you can wire a thin real binding cheaply + safely now, prefer it (closes the reachability gap sooner) — flag which way you went.
