## Things to flag at Step 2.5
1. **Rename boundary — input field only, or the VT method too?** The 075c-broadened semantics live on the **recovery/resume INPUT field** (`ResumeInputs.has_scrollback`, fed from `has_restorable_content()`). `HeadlessVt::has_scrollback()` is a distinct primitive that still literally means "scrollback rows > 0" — renaming *it* to `has_replayable_snapshot` would be semantically WRONG (it checks scrollback, not a snapshot). My default vote: **rename the INPUT field + its feeders/consumers/tests ONLY; leave `HeadlessVt::has_scrollback()` and its `vt.rs`/`durable_scrollback.rs` tests untouched.** Rationale: the name that lies is the input field; the VT method is correctly named.
2. **Raw-tap seam — how to feed raw bytes without coupling `TerminalSession` to the VT?** Today the pump decodes the §6.4 base64 frame back to raw bytes to feed the VT (`actor.rs:171`). The optimization taps raw bytes before/around the encode. My default vote: **expose the raw decoded bytes at the pump's read site (e.g. a raw accessor on the emit, or have `pump()` surface raw alongside the base64 frame) so the actor feeds the VT raw + the wire frame stays base64** — keeping `TerminalSession` a pure byte-pipe (no VT reference inside it). The implementer designs the exact surface and **surfaces it at 2.5**. **This is the one droppable item:** if a clean seam proves to require coupling that violates the byte-pipe design intent, flag it — the raw-tap is an optimization (no correctness gain; frames are currently dropped pre-UDS-forward), so deferring it (re-park) is acceptable rather than forcing an ugly seam.
3. **Toolchain pin — exact version vs floating `stable`?** My default vote: **exact `channel = "1.93.0"` + `components = ["rustfmt", "clippy"]`.** A floating `stable` channel does NOT fix the fmt-drift (stable advances → rustfmt changes) — the whole point is determinism, which needs an exact pin. Confirm `cargo fmt --check` is a no-op immediately after adding the file (it should be — the team already runs 1.93.0); if 1.93.0's rustfmt reformats anything, that reformat is part of THIS commit (one-time).
4. **Commit count — bundle or split the raw-tap?** My default vote: **up to 2 commits** — (1) the three zero-behavior-change hygiene items (rename + `save_tick` test + toolchain pin), (2) the raw-tap refactor (the only hot-path code change → its own commit keeps bisectability clean). Collapse to 1 if the raw-tap lands trivially. Flag the split decision at 2.5.
