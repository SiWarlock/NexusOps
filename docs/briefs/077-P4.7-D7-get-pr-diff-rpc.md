## Things to flag at Step 2.5
1. **Fetch mechanism — how does octocrab get the PR diff?** My default vote: octocrab's PR **diff media-type** (`application/vnd.github.diff` → a unified-diff string) OR the **compare endpoint** (`repos().compare(base, head)` → files-with-patches). **Verify against the vendored octocrab 0.53.1 source** which is available (the D6 Q3 discipline) + pick the one that maps cleanest to `Hunk`/`DiffLine`. Reuse `OctocrabGithubReadClient`.
2. **Read RPC vs Gateway action (LOAD-BEARING).** My default vote: a **read RPC** (per the work order's `get_pr_diff → DiffResult` framing + LESSON 33 — a diff is a transient on-demand read, NOT an event-emitting sync; `get_diff`'s precedent). It does NOT emit (contrast `github.sync_reviews`, a risk-1 Gateway action that EMITS — LESSON 55's untrusted-proposer concern applies to AGENT-initiated network reads; `get_pr_diff` is UI-initiated over the getpeereid-gated UDS, with a mandatory timeout). **If the client-wiring (Q4) proves to fit the Gateway executor far better than the IPC read layer, surface it** — that would reshape D7 from a read RPC to a read-returning action and I'd re-evaluate.
3. **Diff parser placement + reuse.** My default vote: a new unified-diff→`DiffResult` parser (the existing `get_diff` uses git2's STRUCTURED diff, not a text parse, so there's likely nothing to reuse). Site it where the fetch lives (`integrations/github.rs`) or `daemon/src/git/` if git-shaped. Pin the parser with fixtures (hunk headers, +/-/context, the "\ No newline" edge).
4. **Client-wiring into the IPC read layer (the crux).** My default vote: thread an authenticated `GithubReadClient` (or a per-repo client factory resolving the integration-connection keychain auth) into the read dispatch — reusing `OctocrabGithubReadClient` + the LESSON-46 captured-`Handle`+`block_on`+`timeout`. Name the exact construction/injection seam at Step-2.5 (the IPC handlers are `db_path`-only today). Keep it test-seamed (a `FakeGithubReadClient` drives the handler tests).
