# /tdd brief — github_submit_review

## Feature
`github.submit_review` — a **🔴 cat-1, risk-3, NON-standing-grantable** Gateway mutation that submits a PR review **verdict** (`approve` / `request_changes` / `comment`) to a remote PR, SHA-pinned to the approved head (`commit_id`), emitting a `ReviewSubmitted` audit event folding the review into `proj_review`. The **SECOND** GitHub *write* (after D9 `github.merge_pr`); mirrors the `github.merge_pr` executor precedent + the review-specific safety knobs the user steered (2026-06-20). Unlike a merge, a review-submit is a **communication / attestation** write — it does NOT mutate branch/code/repo state — but an `approve` can satisfy branch-protection (merge-gate power), so it is gated identically.

## Things to flag at Step 2.5
1. **Per-hunk inline `comments[]` — INCLUDE now or DEFER?** My vote: **DEFER** to a focused §4.7 follow-on — keep the cat-1 vertical = the PR-LEVEL verdict (event + body + commit_id). The prototype's per-hunk Accept/Reject/Request-fix maps to GitHub's inline `comments[]` array (`{path, line/side/start_line, body}` — each body §15-redacted, each path validated), whose multi-line positioning is fiddly enough to warrant its own slice + security pass. `SubmitReviewArgs.comments` can be a typed-but-empty passthrough now (mechanism present, UI sends none) OR omitted entirely — confirm. **Do NOT silently drop** — record the per-hunk inline-comment surface as a §4.7 follow-on regardless.
2. **`ReviewSubmitted` (new event) vs reuse `ReviewSynced`?** My vote (DECIDED, per the lead's delegation): **a NEW `ReviewSubmitted`** — the D9 `PullRequestMerged`-not-reuse-`PullRequestSynced` precedent (a write mutation emits its OWN typed audit event; reusing a "Synced" read-event muddies the audit semantics — "the user SUBMITTED this" ≠ "we synced an existing review"). Folds `proj_review` identically. Confirm you're aligned.
3. **`commit_id` required or optional?** My vote: **REQUIRED** — audit-integrity + anti-race: the audited review attaches to the exact reviewed head SHA (the merge_pr `sha` precedent). Companion: the live UI Review-submit button needs `head_sha` exposed (the SHARED D9 `head_sha` follow-on — already a §4.7 carry-forward; the mechanism is fake-tested now).
4. **Commit count.** My vote: **2** — (1) the contract freeze (catalog entry + `ReviewSubmitted` + CONTRACT bump + §2.5-seam snapshots), (2) the cat-1 mutation vertical (policy gate-extend + write-client + executor + fold + nudge). The D9 structure; the policy gate-extend rides commit 2 (inseparable from the executor it gates — the D9 FLAG-2 ruling).
5. **`body` conditional-required rule.** My vote: **required-non-empty for `request_changes`/`comment`, optional for `approve`** (GitHub's own 422 rule) — pin both arms (test 7 + the approve-empty-body test). Confirm vs a simpler always-required-body.
