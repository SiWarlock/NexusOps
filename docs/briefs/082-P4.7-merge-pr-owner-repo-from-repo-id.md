# /tdd brief — github_write_owner_repo_from_repo_id

## Feature
Close the **ENTIRE confused-deputy surface** across ALL FOUR GitHub-write executors — `execute_merge_pr`, `execute_submit_review`, `execute_create_pr`, `execute_sync_reviews` (`daemon/src/integrations/executor.rs`) — by resolving GitHub `owner`/`repo` from the **audited `repo_id`** (the resource_ref identity) via `proj_repository.remote_url` — exactly as `get_pr_diff` (D7) does — instead of reading attacker-controllable literal `inputs["owner"/"repo"]`. After the change the **executed target == the audited resource_ref identity by construction at every site.** Executor-internal — NO CONTRACT change.

> **Cross-track ask** (ui track, user-relayed via the lead). A pure **security hardening** (strictly removes the attacker-controllable target). **Lead-ruled (2026-06-20): close all 4 sites in ONE slice via the single shared `resolve_pr_owner_repo` helper** — leaving 2 of 4 paths open is a half-closed surface, not production-grade. **NOT live-exploitable today** (prod client UNAUTHENTICATED → live writes 401→fail-closed; the mutations are UI/IPC-requester-only, getpeereid-trusted local peer) — a **pre-auth** closure (lands before the auth-bootstrap prereq makes the axis live). Verified: **no Finding.**
>
> **Site set + risk:** `merge_pr` (risk-3, cat-1) · `submit_review` (risk-3, cat-1) · `create_pr` (risk-3) · `sync_reviews` (risk-1, the only READ). **LATITUDE (lead):** if `sync_reviews` materially bloats the slice / its review surface, it MAY split to a fast follow-on **083** — but the default is all-4-in-082, and `create_pr` stays in 082 regardless (a risk-3 mutation, not a read).

## Safety framing (the point of the slice — security-reviewer `invariant` across ALL 4 call sites + the shared helper)
A HARDENING of all 4 GitHub-write executors (3 cat-1/risk-3 mutations + 1 risk-1 read). **Three properties pinned at EVERY site:**
- **(a) No literal `owner`/`repo` for the target remains ANYWHERE** — after the change, NONE of `execute_merge_pr`/`execute_submit_review`/`execute_create_pr`/`execute_sync_reviews` reads `inputs["owner"]`/`inputs["repo"]` for the target; the target is resolved from the audited `repo_id` at every site. Pin: a structural grep guard (no literal-owner/repo read in any of the 4 arms) + the behavior tests.
- **(b) ONE resolution authority, mirrors D7/LESSON 59 EXACTLY** — the same `(repo_id, pr_number?) → proj_pull_request → project_id → proj_repository.remote_url → owner/repo` path, the same fail-closed on an unresolvable/missing `repo_id`/unparseable URL (D7's `NotFound` → the executor's `Failed`), via the SINGLE shared `resolve_pr_owner_repo` helper the D7 read path AND all 4 executor sites call — no divergent copy. **Note:** `create_pr` (creating a NEW PR) and `sync_reviews` resolve owner/repo from the **repo** identity (resource_ref repo_id → proj_repository), not a PR row; confirm the helper shape covers repo-only resolution (no `pr_number`) — a Step-2.5 question.
- **(c) Audited == executed at every site** — the `repo_id` resolved is the SAME `repo_id` the resource_ref (the audit/policy identity) carries; the GitHub call targets exactly it. Pin: per-site tests that an `inputs["owner"/"repo"]` pointing elsewhere is IGNORED (the resolved target wins).
