# /tdd brief — github_device_flow_connect

## Feature
The in-app **"Log in with GitHub" device-flow** acquisition (the fast-follow to 083's gh-reuse interim): the daemon runs GitHub's OAuth **device authorization flow** for our GitHub App (public `client_id`, no secret) → receives a **NON-EXPIRING** scoped user-to-server token (`ghu_`) directly via its own outbound poll → stores it in the keychain (via the 083 primitive, per resolved account) → registers the connection. Covers users without `gh`. NO refresh scheduler (L1 non-expiring). An **auth_invalid→re-login** path handles revocation/invalidation (NOT a clock).

> **Decision LOCKED (lead→user):** GitHub App + device flow; **token lifetime = L1 NON-EXPIRING** (disable "Expire user authorization tokens" on the App → device-flow acquisition is **client_id-ONLY, the token does not expire, NO refresh grant, NO client_secret anywhere**; L3 silent-refresh is DEAD — it needs a shippable secret we won't ship). Verified via Context7: App settings → Optional Features → "User-to-server token expiration" → **Opt-out**; with expiration disabled the device-flow response omits `expires_in`/`refresh_token`. Reuses 083's keychain-write primitive + per-account token-selection + the live-writes toggle.

## Safety framing (cat-1 / secret-touching — security-reviewer `invariant`; the in-arc re-review gates live-enablement)
- **§15 #3 (token acquired daemon-side, not inbound on THIS path; no secret in events/rows/logs):** the token arrives via the daemon's OWN outbound poll to GitHub (NOT across the UI→IPC boundary — the UI only triggers the flow + displays the non-secret `user_code`). The token is stored via the 083 keychain primitive (keychain-only; the audit event holds ONLY the keychain_ref); transient token zeroized after store; never logged. **(NB — reconcile w/ LESSON 65:** 5.3b established that an INBOUND secret IS acceptable for the local-trust-boundary profile case; 084 nonetheless stays daemon-OUTBOUND-poll — the LESSON 64/connect_via_gh posture — because GitHub device-flow IS a daemon-side acquisition, so there is no inbound secret on this path. Outbound-poll is the simpler, lower-surface choice here, not a contradiction of either lesson.)
- **§15 #4 (keychain-ref-only):** unchanged from 083 — only the pointer in DB/events.
- **Confused-deputy (post-082):** the acquired token is stored + selected per resolved account (the 083 per-account selection); a multi-account user → multiple connections.
- **L1 non-expiring leak-window — the re-review MUST sign off the mitigation set is real:** minimal scopes (pull_requests/contents/checks only — NOT broad), keychain-ref-only (§15 #4, never DB/logs/events), **instant user-revocability** (revoke the App auth on GitHub → the next call 401s → the auth_invalid card). The re-review explicitly certifies the non-expiring choice is contained by this set.
- **auth_invalid handling (NOT a clock):** a 401/invalidation (user revoked, or GitHub invalidated) → a typed `auth_invalid` → the §11.4 re-login card → re-run the device flow. NO 8h-expiry handling, NO refresh grant (L1).
- **Unchanged supervision:** D9/D10's risk-3 + entry_no_standing_grant + per-action approval still gate EVERY live write; the live-writes toggle (083) still gates enablement post-re-review.
