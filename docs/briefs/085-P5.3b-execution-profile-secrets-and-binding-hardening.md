# /tdd brief — execution_profile_secrets_and_binding_hardening

## Feature
The secret/cat-1 half of Execution Profiles (5.3b): a peer-authed **inbound** `profile.set_secret` keychain write (USER-ruled **Option B**, full live vertical), plus three deterministic binding-hardening pieces — startup keychain self-test → `misconfigured`, §7.2 runtime-status re-derivation on restart, and the `session.profile_change` executor body (the §15 #8 no-silent-account-hop swap).

## Acceptance criteria (what "done" means)

**Piece 1 — `profile.set_secret` inbound keychain write (cat-1, OWN commit):**
- [ ] A peer-authed IPC method `profile.set_secret{execution_profile_id, secret}` writes the inbound `secret` to the OS keychain via `SecretStore::store(profile_keychain_ref(id), secret)` and returns ONLY `{keychain_ref}` — the secret NEVER appears in the result, an event, a row, or a log line (§15 #4; the LESSON 64 no-echo pin).
- [ ] `getpeereid` peer-auth runs **FIRST** (§15 #7), before the secret is read from params — a uid≠daemon-uid peer is rejected with the secret untouched.
- [ ] The inbound secret is held in `Zeroizing` and dropped immediately after the keychain write (the transient is scrubbed; the result carries only the pointer).
- [ ] A per-profile `profile_keychain_ref(execution_profile_id)` derivation (daemon-computed, stable; NOT proposer-supplied) — confused-deputy-safe (the ref is bound to the audited profile id, never to `inputs`).
- [ ] The keychain_ref POINTER is recorded onto the profile's `execution_profiles` row through a **typed audited Gateway Action** (the carry-forward + LESSON 49/LESSON 64 precedent — the secret is already in the keychain; the action carries only the POINTER, registration-only).
- [ ] Fail-closed: an unknown/unparseable `execution_profile_id` is refused (the LESSON 62 resolve-on-unknown precedent); a keychain backend fault surfaces a structural error (no secret in the message), no partial row.

**Piece 2 — startup keychain self-test:**
- [ ] On daemon startup, for each profile with a non-NULL `keychain_ref`, `SecretStore::read` is attempted; a ref that does NOT resolve (or a backend fault) yields runtime status **`misconfigured`** (§5.1). A profile with `keychain_ref=None` is NOT misconfigured (ambient-auth, the seeded default — `available`).
- [ ] The classification is a PURE `self_test_status(has_ref, read_outcome) -> ...` fn (the LESSON 36/LESSON 41 pure-classifier family), unit-tested with `FakeSecretStore` — no real keychain.

**Piece 3 — §7.2 runtime-status re-derivation on restart:**
- [ ] The ExecutionProfile **runtime** status (`active`/`in_use`/`rate_limited`/`auth_expired`/`misconfigured`) is RE-DERIVED from live inputs (live session state + adapter telemetry + the piece-2 keychain self-test), NOT trusted from the persisted row — the persisted `status` is the CONFIG/intended state (the LESSON 41/LESSON 47 live-read-recompute precedent; the worktree-status axis pattern).
- [ ] A PURE `derive_runtime_status(config_status, &RuntimeInputs) -> ExecutionProfile` classifier in strict precedence; total `else`; test-first. A rebuild/restart recomputes it (prove recomputed-not-replayed via a clock/live-input flip on fixed rows, the LESSON 41 discipline).

**Piece 4 — `session.profile_change` executor body:**
- [ ] The `SessionExecutor` gains a `session.profile_change` arm: validate the requested profile is REGISTERED (fail-closed-on-unknown, the `resolve_profile` precedent) → record the swap on the session as an audited event (§15 #8: profile changed only via this approval-gated path, **never silently switched**; the risk-2 approval already gates it).
- [ ] §15 #8 no-account-hop holds: an unknown/unparseable target id → `Failed` before any swap (no mint); the new profile id is recorded (auditable), the prior binding superseded only by the approved change.
- [ ] Brain/Agent can never reach `profile.set_secret` or drive `session.profile_change` (UI/IPC-requester-only where a policy gate applies — the LESSON 60/LESSON 61 `GITHUB_MUTATION_TYPES` deny-before-risk precedent generalized; Brain-may-never-set-a-profile, §15 #8).

**All pieces:**
- [ ] All unit tests in the named test files pass; `/preflight` clean (fmt + clippy -D + check + test).
- [ ] Cross-doc invariant rows updated atomic with the round (orchestrator-written at Step 9 — see below).
- [ ] `security-reviewer` (`invariant` policy) every layer + the mandatory **in-arc live-path re-review** on the inbound-secret path (as 083 did).

## Things to flag at Step 2.5
1. **Secret-flow decomposition (the load-bearing one).** Mirror LESSON 49/LESSON 64 EXACTLY: `profile.set_secret` = a getpeereid-peer-authed IPC **trigger** that does the keychain write ONLY (substrate, no audit event for the write — the secret can't be audited) + returns the pointer; a **separate typed audited Gateway action records the keychain_ref POINTER** onto the registry row (registration-only, the secret already in the keychain, LESSON 49). My default vote: **this split** — it satisfies the 🔴 carry-forward (proposer-reachable register = a Gateway action) AND keeps the secret off any risk-≥1 action by construction. Alternative (fold the pointer-record into the trigger as a System-actor substrate update) is simpler but makes a proposer-driven row write a non-Action — flag if you think the default over-builds.
2. **`profile_keychain_ref` derivation.** Key by `execution_profile_id` (stable, unique) vs by `(provider, account_alias)` (human-readable, but `account_alias` is nullable/mutable). My default vote: **by `execution_profile_id`** — stable + collision-free; the LESSON 64 `keychain_ref_for` is account-keyed because integrations are account-scoped, profiles are id-scoped.
3. **Piece-3 live consumer.** If the restart-time runtime-status consumer genuinely belongs to a later ui-read slice, wire the pure classifier + a `/wired`-checked caller now and name the deferral explicitly (don't ship an unreachable classifier). My default vote: **wire the classifier + the startup recompute pass now; the UI surface is the ui-track follow-on.**
4. **Profile-change swap event.** Reuse `SessionStarted`-shaped recording vs a new `SessionProfileChanged` event. My default vote: **a new minimal audited event** (the swap is a distinct lifecycle fact; reusing SessionStarted muddies "started" vs "re-bound") — confirm the shape.
5. **Commit boundaries.** Piece 1 (the inbound-secret write) is its OWN commit (safety pin). Pieces 2/3/4 each their own (distinct concerns, independently bisectable). My default vote: **4–5 commits**, secret-write isolated; flag if any pair should bundle.
