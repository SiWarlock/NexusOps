# /tdd brief — smoke_cli_rescan_add_project_driver

## Feature
Add a `rescan` subcommand to the `dev-client` smoke CLI that submits the EXISTING `project.rescan` action (risk-0, `X::Project`) with `inputs["path"]=<arg>` — so the user can **add a project from the terminal** (`smoke rescan --path <repo>`) and test the full core loop without any UI dependency. The "add a project" flow has no driver today (no smoke subcommand; the UI add-project flow is a ui-track gap) — this is the 086 pattern applied to `project.rescan`.

## Use case + traceability
- **Task ID:** P4.7 (the §4.7 live-validation CLI-driver arc — the 086 sibling; tracker task under `### 4.7`)
- **Architecture sections it implements:** `ARCHITECTURE.md §6.3` (the `project.rescan` catalog action it submits), `§6.1` (the `submit_action` GatewayPort method), `§5.1`/`§9` (project registry/detection — `project.rescan` detects git state/remote/signals → `ProjectRescanned` → `proj_project`/`proj_repository`).
- **Widens phase scope because:** dev-client tooling (the `dev-client` feature, OUT of the prod binary) exercising the §5.1 `project.rescan` action — not a numbered phase task; the 086 precedent.
- **Related context:** `daemon/src/smoke.rs` (the existing harness — `create`/`queue`/`approve`/`deny`/`kill`/`audit` + the 086 `connect-gh`/`connect`/`set-live-writes`/`create-pr`/`merge-pr`/`submit-review`; `cmd_kill`/the 086 `build_*_request` helpers are the pattern). `project.rescan` catalog: `entry(R::Level0, P::Command, I::None, X::Project, false, true)` — **risk-0** (auto-executes, NO approve step, unlike the 086 risk-2/3 writes), `requires_resource_refs=false` (path input-carried). The `ProjectExecutor` (edges-019) runs it → emits `ProjectRescanned` → `proj_project`/`proj_repository` folded → the project appears in the cockpit.

## Safety framing (NON-cat-1; zero new surface)
- **No bypass / no new mutation surface:** `rescan` submits the EXISTING `project.rescan` `action_type` through the EXISTING `submit_action` — the daemon's policy gate + executor run UNCHANGED. risk-0 means the catalog auto-executes it (the strict catalog-risk-0 re-gate, LESSON §19) — no new auto-execute path, just a CLI that submits an already-risk-0 action. Zero new `action_type`/executor/IPC-method/keychain-write.
- **`dev-client`-gated:** the subcommand lives under the existing `#[cfg(feature = "dev-client")]` gate → OUT of the production `nexusopsd` binary. No production attack surface.
- **No secret:** `inputs["path"]` is a local FS path (not a credential); `ProjectRescanned` strips `user:token@` userinfo at the emit source (LESSON 44) — daemon-side, unchanged.
