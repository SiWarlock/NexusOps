# /tdd brief — smoke_cli_rescan_project_id_mint

## Feature
The `dev-client` smoke `rescan` subcommand (088) mints a `ProjectId` client-side, sets it on the `project.rescan` `ActionRequest.project_id` envelope, and **PRINTS** `project_id=<minted>` — so the submitted `ProjectRescanned` carries a project_id, the `proj_project` projector folds it (the project actually REGISTERS), and the user has the id for the downstream chain (`create --project <id>` → `queue` → `approve`). This closes the user's active "can't add a project" blocker on the CLI surface.

The daemon-side `proj_project` fold is UNCHANGED (it already keys on the envelope id; it only needs the id to be present).

## Things to flag at Step 2.5
1. **Mint in the builder vs in `cmd_rescan`.** (a) `build_rescan_request` mints `Some(ProjectId::new())` and `cmd_rescan` reads it back from `req.project_id` for the print; (b) `cmd_rescan` mints + passes the id into a re-signatured builder. My default vote: **(a)** — minimal signature change, the id lives in one place (the request), the builder stays a pure `args → ActionRequest`, and the existing builder tests can assert the mint directly.
2. **Print format.** A dedicated `project_id=<id>` line vs embedding the id in prose. My default vote: **a dedicated `project_id=<id>` line** — greppable/scriptable, mirrors the runbook chain, unambiguous for the user copying it into `create --project`.
3. **Scope: a `smoke projects` list command?** The plan notes "no `smoke projects` list" as part of the gap. My default vote: **OUT of this slice** — printing the minted id is sufficient to chain `rescan → create --project <id>`; a list view is a separate nice-to-have (flag as a follow-on if you disagree).
