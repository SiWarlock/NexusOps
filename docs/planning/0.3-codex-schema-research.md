## 1. Summary (TL;DR for the daemon team)

- **Sessions** are **JSONL "rollout" files** at `~/.codex/sessions/YYYY/MM/DD/rollout-<ISO8601>-<uuidv7>.jsonl`. Line 1 is `session_meta`; the rest are `response_item` (model items) and `event_msg` (stream events), with `turn_context` records carrying the per-turn policy. The session UUID is in the filename and in `session_meta.payload.id`. **[CONFIRMED-LOCAL]**
- **Programmatic run + resume** is first-class three ways: (a) `codex exec` (one-shot, `--json` for NDJSON events), (b) the **`codex app-server`** JSON-RPC protocol (`thread/start`, `thread/resume`, `command/exec`), (c) the **TypeScript/Python SDKs** (`runStreamed()`, `resumeThread(id)`). Resume: `codex resume [--last|--all|<SESSION_ID>]` / `codex exec resume <SESSION_ID>`. **[CONFIRMED-DOCS]**
- **Stream shape** has two vocabularies: the **public `exec --json` `ThreadEvent`** (`thread.started`/`turn.*`/`item.*`/`error`, with `Usage{input,cached_input,output,reasoning_output}` and item details `command_execution`/`file_change`/`mcp_tool_call`/…), and the **internal rollout** (`event_msg`/`response_item` with `token_count`, `task_started/complete`, `function_call`/`apply_patch`/`patch_apply_end`). Normalize from the public surface. **[CONFIRMED-DOCS + LOCAL]**
- **🔴 MUTATION INTERCEPTION — YES, first-class, two mechanisms.** Codex ships a **Claude-style Hooks system** with a **`PreToolUse`** hook that fires *before* Bash / `apply_patch` / MCP tool calls, receives the tool name + full command on stdin, and can return **`permissionDecision: "deny"`** (or exit 2) to **block the call** — the near-exact analog of Claude's PreToolUse hook NexusOps already routes to the Gateway. Independently, running Codex as an **MCP server** or via **app-server** with `approval_policy = on-request|untrusted` makes it issue `execCommandApproval` / `applyPatchApproval` (or `item/commandExecution/requestApproval`) requests the supervising client must answer `allow`/`deny`. **[CONFIRMED-DOCS]** **Critical caveat:** Codex's own docs call PreToolUse "a guardrail rather than a complete enforcement boundary." The hard enforcement boundary is the **sandbox** (`--sandbox read-only|workspace-write|danger-full-access`). NexusOps must use **both** (hook/approval = adjudication channel into the Gateway; sandbox = OS enforcement) for an INV-SEC-1-grade guarantee — see §4.
- **Auth** is `ApiKey | Chatgpt | ChatgptAuthTokens | AgentIdentity`, stored in `~/.codex/auth.json` (env `OPENAI_API_KEY`/`CODEX_API_KEY`/`CODEX_ACCESS_TOKEN`). `codex doctor` actively warns on multi-auth — maps cleanly to our "no silent account-hopping" profile binding. **[CONFIRMED-DOCS + LOCAL]**
- **Security posture finding [CONFIRMED-LOCAL]:** Codex hardens `auth.json` and `config.toml` to **0600** but leaves `~/.codex/sessions/` at **0755** and rollout files at **0644** — it does **not** self-harden the transcript store. This empirically validates safety rule #11. Recommended enforcement: **launch the codex child with `umask 0077`** so its 0644 files become 0600 and 0755 dirs become 0700 (one-shot `chmod` is insufficient — Codex re-creates files per session). See §1-detail / §4 / §5.

## 2. Session / rollout files

### 2.1 Location, naming, format **[CONFIRMED-LOCAL]**

```
~/.codex/sessions/<YYYY>/<MM>/<DD>/rollout-<ISO8601-with-dashes>-<uuid>.jsonl
# e.g. rollout-2026-05-29T17-26-18-019e75d8-6e9a-7893-839c-da1256d36380.jsonl
```

- **One file per session**, append-only **JSONL** (newline-delimited JSON; one record per line).
- The trailing UUID is the **session id** (a time-ordered **UUIDv7** — note `019e75d8…` prefix), and it also appears as `session_meta.payload.id`. This is the id you pass to `codex resume <SESSION_ID>` / `codex exec resume <SESSION_ID>`.
- A companion **`~/.codex/session_index.jsonl`** maps sessions for the picker: each line `{ "id", "thread_name", "updated_at" }`. **[CONFIRMED-LOCAL]** — useful for "list resumable sessions" without scanning every rollout.

### 2.2 Record shapes (keys observed across ~150 real rollouts) **[CONFIRMED-LOCAL]**

Every line is `{ "type", "timestamp", "payload" }`. Top-level `type` histogram (≈54k records sampled): `event_msg` (≈28k), `response_item` (≈26k), `session_meta` (one per file), `turn_context` (one per turn), `compacted` (rare).

| Record | `type` | Payload keys (verbatim) | Use |
|---|---|---|---|
| Session header (line 1) | `session_meta` | `id, timestamp, cwd, originator, cli_version, source, model_provider, base_instructions` | session identity + provenance |
| Per-turn context | `turn_context` | `turn_id, cwd, model, effort, approval_policy, sandbox_policy, permission_profile, personality, collaboration_mode, realtime_active, truncation_policy, current_date, timezone, developer_instructions, user_instructions, summary` | **records the policy the turn ran under** (profile-binding + recovery) |
| Model tool call | `response_item` / `function_call` | `type, name, call_id, arguments` (arguments = JSON string) | tool-call normalization |
| Tool result | `response_item` / `function_call_output` | `type, call_id, output` | tool result |
| Freeform tool | `response_item` / `custom_tool_call` | name = `apply_patch` (the file-edit tool) | **FS mutation** |
| Assistant text | `response_item` / `message` | role/content | agent message |
| Reasoning | `response_item` / `reasoning` | — | reasoning trace |
| Usage tick | `event_msg` / `token_count` | `type, info{ last_token_usage{input_tokens, cached_input_tokens, output_tokens, reasoning_output_tokens, total_tokens}, total_token_usage, model_context_window }, rate_limits` | **usage normalization** |
| Patch applied | `event_msg` / `patch_apply_end` | `type, call_id, turn_id, changes, status, success, stdout, stderr` | **post-mutation audit signal** |
| MCP tool done | `event_msg` / `mcp_tool_call_end` | `type, call_id, invocation, result, duration` | MCP tool result |
| Turn lifecycle | `event_msg` / `task_started`, `task_complete`, `turn_aborted` | `task_started: turn_id, started_at, model_context_window, collaboration_mode_kind` | status transitions |
| User prompt | `event_msg` / `user_message`; `agent_message` | — | turn boundaries |

Tool names actually seen in `function_call.name`: `exec_command` (shell — the dominant mutation tool, ≈457 of 602), `request_user_input`, `write_stdin`, plus MCP tools (`query_docs`, `codegraph_*`, `resolve_library_id`), `update_plan`. **File edits arrive as `custom_tool_call` name=`apply_patch`** (114 observed). ⚠️ **Tool names are version/config-dependent** — OSS `codex` historically uses `shell`/`local_shell` rather than `exec_command`; the adapter should key on **semantics** (shell-exec vs file-patch vs MCP), not hardcoded names.

### 2.3 Security posture **[CONFIRMED-LOCAL]**

Observed permissions on this machine:

| Path | Mode | Hardened by Codex? |
|---|---|---|
| `~/.codex/auth.json` | `0600` | ✅ yes |
| `~/.codex/config.toml` | `0600` | ✅ yes |
| `~/.codex/sessions/` (dir) | **`0755`** | ❌ **no** |
| `~/.codex/sessions/**/rollout-*.jsonl` | **`0644`** | ❌ **no** |
| `~/.codex/hooks.json` | `0644` | ❌ no |

→ **Safety rule #11 is validated**: Codex does *not* pre-harden the transcript store, and rollout files contain full transcripts (including command output that may carry secrets). NexusOps must enforce `0700`/`0600` itself. **Best enforcement: spawn the `codex` child process with `umask(0077)`** so newly-created dirs become `0700` and files `0600` *without* racing Codex's per-session file creation. A one-time `chmod` of the dir is necessary-but-insufficient because Codex re-creates rollout files `0644` on every new session.

## 3. App-server / run protocol + resume

### 3.1 The three programmatic surfaces **[CONFIRMED-DOCS]**

1. **`codex exec` (non-interactive / automation).** Alias `codex e`. Flags: `--json` (a.k.a. `--experimental-json`) → newline-delimited `ThreadEvent` stream on stdout; `--output-last-message,-o PATH`; `--color`; `--ephemeral` (run **without** persisting a rollout — NexusOps should *not* use this; it needs the rollout for recovery). Resume: `codex exec resume <SESSION_ID>`.
2. **`codex app-server` (Experimental) — JSON-RPC.** `--listen stdio:// | ws://IP:PORT | unix:// | unix://PATH | off`, `--ws-auth capability-token | signed-bearer-token`. **Note the `unix://` transport** — Codex can listen on a UDS, aligning with NexusOps's own UDS posture. Methods include `thread/start`, `thread/resume`, `command/exec`, and the approval requests in §4.
3. **`codex mcp` (Experimental).** Runs Codex as / manages MCP servers (`add|list|remove|get|login|logout`). The MCP server mode is where Codex issues `execCommandApproval` / `applyPatchApproval` to the connected client (§4). *(No `codex proto` subcommand in current docs — older `proto` appears superseded by `app-server`.)*
4. **SDKs** (TypeScript / Python) wrap the above: `codex.startThread()` / `thread.runStreamed()` / `codex.resumeThread(id)` / `thread.run()`. **[CONFIRMED-DOCS]**

### 3.2 Resume / continuation **[CONFIRMED-DOCS]** → maps to our `ResumeMode`

| Codex mechanism | What it does | NexusOps `ResumeMode` |
|---|---|---|
| `codex resume <SESSION_ID>` (interactive) / `codex exec resume <SESSION_ID>` | Re-open a stored session by UUID; reconstructs turn history from the rollout | **`resumed`** (true continuation) |
| app-server `thread/resume { threadId, excludeTurns?, initialTurnsPage?, model?, modelProvider? }` | JSON-RPC resume; can exclude/paginate history; can override model/provider | **`resumed`** (programmatic) |
| `codex resume --last` / `--all` | Most-recent in cwd / across all cwds | session-selection policy for recovery |
| Read the rollout JSONL directly (no live process) | Replay the persisted transcript to rebuild UI/projection state | **`replayed`** (no live agent) |
| `codex exec` fresh (no resume) | New session | **`relaunched`** |
| Re-attach to an already-running app-server thread | Live process still up | **`reattached_live`** |

**app-server `thread/resume` request example** **[CONFIRMED-DOCS]**:
```json
{ "method": "thread/resume", "id": 11,
  "params": { "threadId": "thr_123", "excludeTurns": true,
              "initialTurnsPage": { "limit": 20, "sortDirection": "desc", "itemsView": "summary" } } }
```
⚠️ **ID-space note [GUESS / needs live-Codex]:** the CLI resumes by **UUID** (the rollout filename id, e.g. `019e75d8-…`), while app-server/SDK examples show `threadId: "thr_123"`. These are very likely the same session in two notations (the `thr_` form may be an app-server alias), but **confirm they interconvert** before the adapter keys recovery off one or the other.

## 4. 🔴 Mutation interception (highest priority, safety-critical)

**Answer: YES — Codex has first-class, supervisor-facing interception, via two complementary mechanisms. This is the single best piece of news for 3.3: NexusOps can mirror its existing Claude PreToolUse→Gateway loop almost 1:1.**

### 4.1 Mechanism A — the Hooks system (the direct PreToolUse analog) **[CONFIRMED-DOCS]**

Codex ships a **Claude-style hooks engine**. Hook events: `SessionStart, SubagentStart, **PreToolUse**, **PermissionRequest**, PostToolUse, PreCompact, PostCompact, UserPromptSubmit, SubagentStop, Stop`.

- **`PreToolUse` fires before Codex invokes Bash, file edits via `apply_patch`, and MCP tool calls.** It receives JSON on **stdin** and returns a decision on **stdout** (or via exit code).
  - **Input (stdin):** `{ turn_id, tool_name ("Bash" | "apply_patch" | MCP name), tool_use_id, tool_input{ command, … } }`.
  - **Output (stdout) — deny (blocks the call):**
    ```json
    { "hookSpecificOutput": { "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": "Routed to NexusOps Gateway; not approved." } }
    ```
  - **Output — allow, optionally rewriting the command:**
    ```json
    { "hookSpecificOutput": { "hookEventName": "PreToolUse",
        "permissionDecision": "allow",
        "updatedInput": { "command": "…" } } }
    ```
  - Or **exit code `2` + reason on stderr** to deny. **A denied PreToolUse blocks that tool invocation.**
- **`PermissionRequest`** fires when Codex is about to ask for approval (shell escalation / managed-network). Output `{ "hookSpecificOutput": { "hookEventName": "PermissionRequest", "decision": { "behavior": "allow" | "deny", "message": "…" } } }`. **"Any `deny` wins"** across multiple matching hooks.
- **Configuration** — `hooks.json` or `[hooks]` in `config.toml`, with **regex `matcher`** on `tool_name`:
  ```json
  { "hooks": { "PreToolUse": [ { "matcher": "^(Bash|apply_patch)$",
      "hooks": [ { "type": "command", "command": "/path/to/nexusops-gate", "timeout": 30,
                   "statusMessage": "Adjudicating via NexusOps Gateway" } ] } ] } }
  ```
  Discovery precedence: `~/.codex/{hooks.json,config.toml[hooks]}` → `<repo>/.codex/…` → plugin-bundled → enterprise `requirements.toml`. **[CONFIRMED-LOCAL]:** this machine's `config.toml` carries a `[hooks.state]` table with `trusted_hash` entries for `hooks.json:pre_tool_use:0:0` and `…:stop:0:0` — i.e. Codex tracks a trust hash of each hook command and re-prompts if it changes (a tamper check the adapter must satisfy: register the gate command once, keep its hash stable).

→ **This is the load-bearing win.** The CodexAdapter can install a `PreToolUse` hook command that does exactly what NexusOps's Claude hook does: serialize the intercepted tool call, hand it to the Action Gateway, **block** on the daemon's decision (fail-closed 5-min wait like 4.0b-2), and emit `allow`/`deny` back. The Claude→Gateway plumbing is reusable; only the I/O envelope differs (`hookSpecificOutput.permissionDecision` vs Claude's hook JSON).

### 4.2 Mechanism B — the native approval protocol (app-server / MCP) **[CONFIRMED-DOCS]**

When Codex runs as an **MCP server** or under **app-server** with `approval_policy = on-request` (or `untrusted`), it issues server→client approval **requests** and blocks until answered:

- **MCP interface:** `execCommandApproval` and `applyPatchApproval` JSON-RPC requests; client replies `allow` / `deny`.
- **app-server:** sequence `item/started` → `item/commandExecution/requestApproval` (carries `command`, `cwd`, `additionalPermissions`, `networkApprovalContext`) → client responds `accept` / `decline` / `acceptForSession` (or policy amendment) → `serverRequest/resolved` → `item/completed`.
- `acceptForSession` maps naturally onto a NexusOps **permit-class** (4.0b-2-F2) — a scoped, time/▶session-bounded standing approval.

This is the cleaner integration if NexusOps drives Codex over a socket (app-server `unix://`) instead of as a hooked CLI child — the approval handshake is in-band, no separate hook process.

### 4.3 Approval × sandbox matrix (the enforcement model) **[CONFIRMED-DOCS]**

- **`--ask-for-approval, -a`**: `untrusted | on-request | never` (config `approval_policy` also has `on-failure`: run in sandbox first, escalate to user on failure).
- **`--sandbox, -s`**: `read-only | workspace-write | danger-full-access` (config `sandbox_mode`; `[sandbox_workspace_write] network_access = true/false`). Bypass: `--dangerously-bypass-approvals-and-sandbox` / `--yolo`; `--full-auto` deprecated → `--sandbox workspace-write`.

> **⚠️ INV-SEC-1 nuance (must be in the 3.3 brief).** Codex's docs explicitly call PreToolUse **"a guardrail rather than a complete enforcement boundary"** — the agent may reach FS/shell through a tool path the hook doesn't match. So the hook/approval channel alone is **not** a sufficient "single audited mutator" guarantee. NexusOps must layer it: **(1)** the PreToolUse/approval channel routes every *intended* mutation into the Gateway (audit + adjudication), **and (2)** run Codex under `--sandbox read-only` (or `workspace-write` scoped to an approved worktree) as the **OS enforcement boundary** so anything that slips the hook still cannot mutate outside policy. Defense-in-depth: hook = adjudication+audit; sandbox = containment. This mirrors how NexusOps already treats the Claude hook as adjudication, not containment.

## 5. Auth / profile

- **`CodexAuth` enum [CONFIRMED-DOCS]:** `ApiKey` · `Chatgpt` (browser OAuth, persisted) · `ChatgptAuthTokens` (external/ephemeral tokens — **headless OAuth via token injection**, useful for daemon-driven runs) · `AgentIdentity` (access-token).
- **Storage:** `~/.codex/auth.json` (**0600**, hardened by Codex — confirmed local). Env overrides: `OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`.
- **ChatGPT login flow (app-server):** `account/login/start {type:"chatgpt"}` → returns `authUrl`+`loginId` → notification `account/login/completed {loginId, success, error}`; `account/updated {authMode, planType}` whenever auth mode changes. **[CONFIRMED-DOCS]**
- **Multi-auth detection:** `codex doctor` **warns** when `auth.json` holds ChatGPT tokens *and* `OPENAI_API_KEY` is in env (multiple auth methods configured). **[CONFIRMED-DOCS]** → directly supports our **"no silent account-hopping"** rule: NexusOps resolves and **pins one** auth method at approval time, records it in `SessionStarted` (execution-profile binding, safety rule #8), and refuses to launch if the environment presents ambiguous auth.
- **Profile selection:** `--profile,-p NAME` layers `$CODEX_HOME/<NAME>.config.toml` over base config; `--config,-c KEY=VALUE` for ad-hoc overrides; `--model,-m`. `config.toml` keys `model`, `model_provider`, `model_reasoning_effort` (confirmed local: `model="gpt-5.5"`, `model_reasoning_effort="xhigh"`), and per-project `[projects."<path>"] trust_level`. **[CONFIRMED-LOCAL + DOCS]**
- **Profile binding handle:** the **execution profile = (auth method, `model`+`model_provider`, `approval_policy`, `sandbox_mode`, `permission_profile`, `cwd`)**, all of which the rollout's `turn_context` records per turn — so the adapter can both **set** the profile at launch and **verify** it from the rollout/stream during recovery (no silent drift). **[INFERRED from CONFIRMED-LOCAL turn_context keys]**

## 7. Open questions / needs live-Codex validation (the eventual HITL)

1. **PreToolUse blocking semantics under load** — confirm a `deny` (or exit 2) from the hook **actually halts** the `exec_command`/`apply_patch` and that Codex surfaces the denial cleanly (no retry-around). Confirm the **fail-closed wait** (daemon takes seconds) doesn't trip the hook `timeout` (config'd `timeout` in seconds) — may need a generous/disabled hook timeout, mirroring 4.0b-2's 5-min Gateway wait. **HITL-critical.**
2. **Coverage of the hook** — enumerate which tool paths PreToolUse actually intercepts in the **target OSS version** (docs say Bash + `apply_patch` + MCP; verify no un-hooked FS path like an MCP filesystem server or a built-in editor tool). Drives whether `--sandbox read-only` is mandatory vs belt-and-suspenders.
3. **app-server stability + transport** — `codex app-server` is marked **Experimental**; confirm `unix://` transport + `thread/resume` + the `requestApproval` handshake are stable in the pinned version, and pin that version.
4. **Session-id interconversion** — confirm CLI `<SESSION_ID>` (rollout UUID) ↔ app-server `threadId` (`thr_…`) are the same session / convertible (§3.2).
5. **Tool-name canonicalization** — the OSS `codex exec --json` item names (`command_execution`/`file_change`) vs the desktop rollout names (`exec_command`/`apply_patch`); capture **fixtures from the actual OSS CLI version** the daemon will ship against, not just the desktop rollouts here.
6. **Sandbox ↔ approved-worktree binding** — verify `workspace-write` can be scoped to exactly the approved git worktree and that `network_access=false` holds, so the sandbox enforces the same boundary the Gateway approved.
7. **Resume fidelity** — does `resume` replay tool *side-effects* or only the transcript? (It should only reconstruct conversation state; mutations already happened.) Confirm so recovery doesn't double-apply.
8. **`auth.json` rotation / `ChatgptAuthTokens` injection** — confirm the headless token-injection path for a daemon-launched session without an interactive browser login, and how expiry/refresh surfaces.
9. **Perms enforcement** — confirm `umask 0077` on the child yields `0700`/`0600` for Codex-created session dirs/files across the target version (and that Codex doesn't `chmod` them back).

## 8. Build-3.3 implications (deterministic-now vs blocked)

### Deterministically buildable **now**, test-first against fixtures:

- **Rollout parser** → normalized `HarnessAdapter` types.
