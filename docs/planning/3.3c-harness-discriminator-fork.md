## Context

Codex launches under a `PreToolUse` hook (`nexusops-codex-gate`). For each Codex tool-call the hook normalizes the envelope and sends the daemon an `intercept` RPC. The daemon's classifier maps **tool-name → §6.3 `agent.*` action type → risk → adjudicate (approve/deny) → verdict → allow/deny** the tool. This is the EXACT 4.0b-2/043 loop already proven for Claude.

The friction: **the daemon's classifier today hardcodes `Harness::Claude`.** It knows Claude's tool vocabulary (`Bash`/`Edit`/`TodoWrite`…) and Claude's MCP coverage semantics (**BestEffort → Deny**). Codex diverges on two axes:

- **Tool names differ** — Codex emits `exec_command`/`shell`/`local_shell`/`apply_patch`/`mcp__*`, none of which are Claude tool names. In particular `apply_patch` (Codex's file edit) is **not** a Claude tool.
- **MCP coverage differs** — Codex MCP is **Guaranteed-interceptable → Adjudicate** (route it through the Gateway for approval), whereas Claude MCP is **BestEffort → Deny**.

So a Codex tool-call fed to the unmodified Claude classifier mis-classifies: `apply_patch` → UnmappedTool → DENY; Codex `mcp__*` → BestEffort → DENY. The brief's own acceptance test #6 requires `McpTool → agent.mcp_tool` (Adjudicate) — which the Claude classifier cannot produce.

---

## 1) What B1 and B2 each ARE

### B1 — handler untouched (the brief's default assumption)
The Codex hook feeds Codex tool-names into the **UNCHANGED** Claude classifier, with **no discriminator**; the daemon never learns the payload is Codex. To make `apply_patch` adjudicate as an edit, the **hook must rewrite the tool identity** (`apply_patch` → `"Edit"`, a Claude name) before sending. Even then it **cannot** express Codex-MCP's Guaranteed-interceptable semantics — Codex MCP would be denied outright rather than routed for approval.

- **Mechanism:** identity-faking in the hook + reliance on the Claude classifier's name table.
- **Verdict:** cannot satisfy the brief's spec (test #6); requires a vendor-identity lie.

### B2 — optional harness tag + 2-arm classifier (recommended)
Add an **OPTIONAL** `harness: Option<Harness>` field to the **daemon-internal** `HookPayload`. The Codex hook stamps `harness = "codex"`; the Claude hook stamps nothing → defaults to Claude. The daemon's `map_to_action_type` branches on that tag:

- **codex** → a Codex classifier: `exec_command`/`shell`/`local_shell`/`bash` → `agent.bash` · `apply_patch` → `agent.file_edit` · `mcp__*` → `agent.mcp_tool` (Adjudicate) · unknown → `CoverageGap` → **deny**.
- **absent / claude** → the **EXISTING** Claude classifier, **byte-identical** to today.

**Everything downstream of classification is shared and unchanged** — `submit_action` / `decision_sink` / the intercept wait-class / verdict emit / `methods.rs` / `writer.rs` / `listener.rs`. Only the name→action-type step branches (the parser), keyed by a tag set by our own trusted binary.

## 2) INV-SEC-1 / §15 implication + reversibility

### B1
INV-SEC-1 holds only **incidentally** — partly because mis-classification happens to land on DENY. This is **brittle**: if Codex ever ships a tool whose name **collides** with a Claude tool name, the Claude classifier could mis-map it — worst case onto a benign auto-allow (`agent.todo_write`). Safety is **accidental, not by-construction**. (And it fails the brief regardless.)

### B2
INV-SEC-1 holds **by construction**. The only thing that branches is the name→action-type mapping; the **risk assignment** (from the frozen §6.3 catalog), approval-gating, audit-before-verdict, and fail-closed behavior are the **shared, already-proven path**.

**Reversible-toward-stricter — YES.** The default (no tag) is the *strictest* reading: a Codex tool-call routed through the Claude classifier → `UnmappedTool` → **DENY**. Both classifier arms are **deny-unknown**. The Codex arm has **zero auto-allow** in this slice (`update_plan`/`request_user_input` deny today). Dropping the tag reverts to pure-Claude-deny. Adding the tag can only make a Codex tool adjudicate **more correctly** (route `apply_patch` for approval instead of deny-by-accident) — it **never opens a path that was closed**.

---

## 3) Residual to PARK for the user vs safe-by-construction

### B2 — safe-by-construction, NO user-park
- The `harness` tag is **stamped by our trusted hook binary** (from its `--harness` flag) into the daemon-internal payload. It is **NOT** read from Codex stdin and is **not agent-settable**.
- **Spoof analysis (worst case, out of threat model — would require compromising our own binary):** forcing the tag only selects the "wrong" classifier. Both arms deny-unknown; risk is **catalog-authoritative + daemon-side**. The only auto-allow anywhere is Claude's `TodoWrite → agent.todo_write`, and `TodoWrite` is a benign plan-update no-op (no FS/shell/mutation). **No tag value converts a real mutation into a silent allow.** Codex `mcp__*` → `agent.mcp_tool` is risk-2, approval-gated, never auto-allowed.
- **The only deferral** is benign-Codex-tool auto-allow *tuning* (`update_plan`/`request_user_input` are deny-unknown today) — a **non-safety refinement** that ships **stricter** (deny) now. That's a **carry-forward**, not a user-park.

### B1
Carries the latent **name-collision fragility** above (a residual worth flagging) **and** fails the brief — moot.

**Conclusion: B2 leaves no INV-SEC-1 residual requiring a user-park.** It is rulable under the away-dial.

---

## 4) Recommendation — B2

B2 is the only option that:
- **Meets the brief's own spec** (test #6 `McpTool → agent.mcp_tool`/Adjudicate; the Guaranteed-interceptable Codex-MCP semantics).
- **Keeps the proven Gateway adjudication loop literally unchanged** (only the parser branches).
- **Ships at the strictest end** — deny-unknown both arms, no Codex auto-allow.
- **Is reversible-toward-stricter** — drop the tag → pure-Claude-deny.
- **Leaves no INV-SEC-1 residual to park.**

**Scope flag:** B2 touches `daemon/src/harness/claude/intercept.rs` (the `HookPayload` field + the 2-arm branch) — beyond the brief's listed file set, but the brief explicitly anticipated this as a Step-2.5 flag. `methods.rs`/`writer.rs` are unchanged.

**CONTRACT:** **no bump** — `harness` is an optional **daemon-internal** `HookPayload` field, not a `shared/` wire contract; the §6.3 `agent.*` catalog + the `intercept` RPC stay frozen.

**On a B2 ruling**, the orchestrator sends the implementer `APPROVED.` (the rest of the Step-2.5 test design — 8 asserts + coverage map, incl. the verified write-boundary-only sandbox assertion and the no-live-spawn pin — is already sound).
