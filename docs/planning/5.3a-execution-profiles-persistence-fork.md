## THE FORK (load-bearing, §15 #8-adjacent) — how to persist & populate profiles

The "schema shape" turned out to be a persistence-PATTERN choice that the RED tests bake in.

### Option A — Event-sourced projection (the established daemon pattern)
A `ExecutionProfileRegistered` event flows through the log → a `proj_execution_profile` read-model the projector folds. Rebuildable.
- **Pros:** uniform with the entire daemon (`proj_project`, `proj_integration_connection` both built this way); rebuild-safe (LESSON §4/§17); audit trail automatic. This is what **LESSON §48 chose TWICE** — by deferring the §2.8 durable-registry-with-canonical-row for projects + integrations.
- **Cons:** models stable config as an event stream (a mild conceptual stretch; config isn't really "events").

### Option B — Durable registry / canonical row (what DATA_MODEL §2.8 literally specifies)
The `execution_profiles` row IS the source of truth, written directly + backed up with the DB, NOT rebuilt from events (a mutation still emits an audit event for the trail).
- **Pros:** matches the data-model spec; config-as-config (arguably more correct for stable account setup); the eventual intended target.
- **Cons:** introduces a NEW persistence pattern mid-build (the daemon's FIRST true durable registry); a bit more code + the canonical register-mutator surface the project has so far deferred (LESSON §48).

### DECISION (2026-06-20): the user ruled **Option B** (durable registry / canonical row)
The user chose B — the DATA_MODEL-§2.8 canonical row, the literal spec target (avoids a later A→B migration; LESSON §48's twice-deferred canonical register-mutator is now BUILT). Both sub-decisions YES.

_Deliberation record (retained): the orchestrator's original recommendation was **Option A** — consistency with the established projection pattern, rebuild-safe, lowest risk, defer the §2.8 registry (LESSON §48). The honest caveat that carried the decision: B is what the data-model literally specifies, and choosing it now avoids a later A→B migration — which the user weighted higher than the lower-risk A._

## Coupled sub-decisions (orchestrator rec — same under A or B)

1. **Where do profiles come from in 5.3a?** Seed ONE default profile at daemon cold-start via the audited **System-actor mechanism** already used to register the Device/LocalRunner (**LESSON §10** — the daemon's own substrate, not a proposer intent). Full multi-profile management + UI = a later slice. Unblocks real resolution without building profile-CRUD now.
2. **Unknown profile id requested?** **FAIL-CLOSED** (refuse to launch — can't bind to a non-existent profile; no silent mint) when an id is given but unknown; **use the default** when no id is given. Makes §15 #8 "no silent account-hop" literal (today's placeholder-mint is exactly the gap being closed).
